# HOMER Mapping Explorer — Visualisation Fix Plan

Scope: address the broken/asymmetric surface rendering in `outputs/gui/index.html`
and the related polish items, while keeping the existing Plotly stack. A
Niivue migration is outlined at the end as the alternative path if we decide
the harmonisation gap is too large to close with Plotly tweaks.

All changes are made to the Python source — primarily
`homer/src/homer/viz/gui.py` (which holds `_HTML_TEMPLATE` and the layer
builders). `outputs/gui/index.html` is then regenerated by re-running
`homer/pipeline/08_build_gui.py`.


## Root cause: the surface toggle is one mutually-exclusive control

The current `viewMode` is a single 3-way segmented button group
(`parcels` | `human_surface` | `mouse_atlas`). `drawPlots()` switches both
panels together, so there is no state in which the human pial surface and
the mouse atlas shell render simultaneously. The fix is to make surface
visibility a per-species setting.

### Change 1 — split the toolbar controls

In `_HTML_TEMPLATE` (`gui.py`), replace the single `#viewMode` block with two
independent segmented controls:

```html
<span class="small muted">Mouse</span>
<span class="seg" id="mouseView">
  <button data-mview="points" class="active">Points</button>
  <button data-mview="atlas">Shell + points</button>
</span>
<span class="small muted">Human</span>
<span class="seg" id="humanView">
  <button data-hview="points" class="active">Points</button>
  <button data-hview="surface">Surface</button>
</span>
```

### Change 2 — state and event wiring

```js
let state = {
  model: DATA.models[0].id,
  selected: null,
  colorMode: 'evidence',
  mouseView: 'points',   // 'points' | 'atlas'
  humanView: 'points',   // 'points' | 'surface'
};
```

The single `viewMode` listener in `init()` is replaced by two listeners
(`#mouseView` and `#humanView`) that each call `drawPlots()` and
`updateSelection(state.selected)`.

### Change 3 — `drawPlots()` builds each panel independently

Today `drawPlots()` branches on `state.viewMode` and rebuilds both panels.
Refactor into two builders so the panels are independent:

```js
function buildMouseTraces() {
  const traces = [];
  if (state.mouseView === 'atlas' && hasLayer('mouse_shell')) {
    const shell = layer('mouse_shell');
    traces.push(meshTrace(shell, {color:'#b9c1c5', opacity:0.18}));
    traces.push(shellHeatTrace(shell));   // see Change 4
    traces.push(mousePointTrace());
    traces.push(emptyMeshTrace());        // alpha-hull slot for selection
    traces.push(emptyScatterTrace());     // selected-points slot
  } else {
    traces.push(mousePointTrace());
    traces.push(emptyScatterTrace());     // selected-points slot
  }
  return traces;
}

function buildHumanTraces() {
  const traces = [];
  if (state.humanView === 'surface' && hasLayer('human_surface')) {
    const surf = layer('human_surface');
    traces.push(meshTrace(surf, {color:'#c7ccd0', opacity:0.24}));
    traces.push(surfaceHeatTrace(surf));
    traces.push(emptyScatterTrace());     // off-surface points slot
  } else {
    traces.push(humanPointTrace());
    traces.push(emptyScatterTrace());     // selected-points slot
  }
  return traces;
}
```

Then `drawPlots()` just calls these and `Plotly.react()`s each div. Titles
are set from the species view, not from a combined mode.

### Change 4 — symmetric mouse-shell heat overlay (per your "yes" answer)

The human side projects coupling mass onto fsaverage5 vertices through
`parcel_stencil`. We mirror that for the mouse shell.

In `gui.py`, extend `_build_mouse_shell_layer()` to compute, for each mouse
parcel, the nearest-K vertices on the DSURQE/CCFv3 shell within a distance
cutoff, with Gaussian weights (same shape as `_build_human_surface_layer()`):

```python
from scipy.spatial import cKDTree
tree = cKDTree(coords)
xyz = mouse_ad.var[["x", "y", "z"]].to_numpy(dtype=float)

stencils, distances = [], []
for point in xyz:
    d, idx = tree.query(point, k=stencil_k)
    d = np.atleast_1d(d).astype(float)
    idx = np.atleast_1d(idx).astype(int)
    valid = np.isfinite(d) & (d <= max_distance_mm)
    if not np.any(valid):
        stencils.append([])
        distances.append(float(round(float(np.nanmin(d)), 3)))
        continue
    d, idx = d[valid], idx[valid]
    w = np.exp(-(d ** 2) / (2.0 * sigma_mm ** 2))
    w = w / w.sum()
    stencils.append([[int(i), float(round(float(wi), 5))]
                     for i, wi in zip(idx.tolist(), w.tolist())])
    distances.append(float(round(float(d.min()), 3)))

return {
    ...,
    "stencil_k": int(stencil_k),
    "max_distance_mm": float(max_distance_mm),
    "parcel_stencil": stencils,
    "surface_distance_mm": distances,
}
```

Suggested defaults for mouse (smaller brain, mm-scale): `stencil_k=10`,
`max_distance_mm=1.5`, `sigma_mm=0.6`. Tune by inspection — print
`min/median/max` of `surface_distance_mm` after the first build and adjust
so most parcels land on the shell.

On the JS side, add `shellHeatTrace(shell)` (same shape as
`surfaceHeatTrace`) and a `renderMouseShellHighlights(indices)` that paints
intensity onto the mouse shell from `mouse_shell.parcel_stencil[i]` for each
selected mouse parcel — i.e. the mouse analogue of
`renderHumanSurfaceHighlights`, but driven directly by `indices` (the
selection) rather than by `agg.topHumans`.

### Change 5 — `renderActiveHighlights()` routes per species

```js
function renderActiveHighlights(indices, agg) {
  // Mouse panel
  if (state.mouseView === 'atlas' && hasLayer('mouse_shell')) {
    renderMouseShellHighlights(indices);          // new
    // selected-points trace index in the atlas layout (see buildMouseTraces)
    renderMousePointSelection(indices, 4);
  } else {
    renderMousePointSelection(indices, 1);
  }

  // Human panel
  if (state.humanView === 'surface' && hasLayer('human_surface')) {
    renderHumanSurfaceHighlights(indices, agg);   // existing, retargeted to its trace indices
  } else {
    renderHumanPointHighlights(agg, 1);
  }
}
```

Trace indices must match the order produced by `buildMouseTraces` /
`buildHumanTraces`. The current code's hard-coded `restyle(..., [1])` etc.
should be replaced with named constants per layout to avoid drift.


## Other polish items (worth doing while we're in there)

These are independent of the per-species split; pick what you want when we
implement.

### Unify the quantitative colorscale

`VIRIDIS` is used for entropy and human-point heat. `SURFACE_COLORS`
(cream → blue → orange) is used for the human surface heat. Two scales for
the same conceptual axis (coupling mass / uncertainty) is confusing.
Recommendation: drop `SURFACE_COLORS`, use viridis everywhere a 0–1
quantitative value is shown (both surfaces, both point-size encodings), and
update the toolbar `.gradient-swatch` to match. Diverging colors (the
orange-on-cream) should be reserved for selection emphasis, not heat.

### Selection coloring on the mouse atlas view

`renderMouseAtlasHighlights` currently sets `'marker.color': [['#111827']]`,
flattening all selected mouse parcels to a single black. Either keep the
base color (trust/network/entropy) and only change `marker.size` and
`marker.line` to emphasise selection, or use the accent orange consistently
across both panels for "selected".

### Linked cameras

After the first `Plotly.react()`, attach `plotly_relayout` listeners that
mirror `scene.camera` between the two panels:

```js
plotMouse.on('plotly_relayout', ev => {
  if (ev['scene.camera']) Plotly.relayout('plotHuman', {'scene.camera': ev['scene.camera']});
});
plotHuman.on('plotly_relayout', ev => {
  if (ev['scene.camera']) Plotly.relayout('plotMouse', {'scene.camera': ev['scene.camera']});
});
```

Guard against feedback loops with a single shared `lock` flag.

### Trace-index constants

Hard-coded `[1]`, `[2]`, `[3]` in `Plotly.restyle` calls will silently break
the moment we add or remove a trace. Define per-layout maps, e.g.
`TRACE_IDX.mouse.atlas = {shell:0, heat:1, points:2, hull:3, selected:4}`,
and reference them everywhere.

### Plot-container heights

`#plotMouse, #plotHuman { width:100%; height:100% }` relies on the grid
sizing its parent. At narrow widths (`@media (max-width: 1120px)`) the
`.right` panel wraps onto the same row and the plot row sometimes collapses
briefly during resize. Adding `min-height:0` to `.brain-grid` and an
explicit `aspect-ratio` (or fixed-height fallback) on `.plotbox` makes
resizes less janky.

### Toolbar legend

When `state.colorMode === 'entropy'` and a surface is on, the legend should
show the same colorscale as both the points and the mesh intensity. Easy
once the palette is unified.


## Alternative path: Niivue

If we want the two panels to *feel* like one neuro tool rather than two
co-located Plotly plots, Niivue is the right migration target.

Why it fits:

- Single WebGL viewer, one CDN script tag.
- Renders volumes + surfaces with the same overlay model, so mouse shell
  and human pial would use the same code path.
- Native support for per-vertex scalar overlays — our `parcel_stencil`
  output drops in as a per-vertex intensity array per selection.
- Camera, lighting, slicing all consistent across panels (and would let us
  add 2D slice views later without another package).

Rough migration shape:

1. Convert the DSURQE shell and fsaverage5 pial outputs to GIfTI/MZ3 files
   in `outputs/gui/meshes/` (Niivue loads either; MZ3 is smaller).
2. Replace `_HTML_TEMPLATE`'s two `<div id="plotMouse">` / `<div id="plotHuman">`
   with two `<canvas>` elements and Niivue instances pointing at the mesh files.
3. On selection, build per-vertex intensity arrays in JS exactly as we do
   now and push them as overlays via `niivue.setMeshLayerProperty`.
4. Keep the existing aside / right panel HTML unchanged; only the centre
   visualisation block changes.

Cost estimate: comparable to doing all the Plotly polish items, plus mesh
conversion. Benefit: visuals harmonise by construction, and future
additions (e.g. showing the raw functional volume underneath, or
slice-through views) become cheap. If we expect to keep extending the GUI
the migration probably pays for itself.


## Rebuild step

After editing `homer/src/homer/viz/gui.py`:

```bash
cd homer
python pipeline/08_build_gui.py
```

This writes `outputs/gui/gui_data.json` and `outputs/gui/index.html`. The
mouse-stencil change increases `gui_data.json` size (and therefore the
embedded `DATA` blob in `index.html`); current file is ~6.8 MB, expect
roughly +0.5–1 MB depending on `stencil_k` and `max_distance_mm`.


## Suggested implementation order

1. Add `parcel_stencil` to `_build_mouse_shell_layer()` and verify
   `surface_distance_mm` distribution looks reasonable.
2. Split `viewMode` into per-species controls and refactor `drawPlots()`.
3. Introduce trace-index constants so highlights don't depend on positional
   `restyle` magic numbers.
4. Add `renderMouseShellHighlights` and route per-species in
   `renderActiveHighlights`.
5. Unify the quantitative colorscale (viridis everywhere) and update the
   toolbar swatch.
6. Linked cameras + selection-color tidy-up.
7. Re-run `pipeline/08_build_gui.py` and eyeball both panels in
   `outputs/gui/index.html`.

Niivue migration is an alternative to (2)–(6) rather than an addition.
